# PDF 冗余案例分析

一次完整的案例分析。**按顺序做完六步，不许跳步。**

前提：**文件不会凭空获得信息。** 变大的字节要么是真的新信息（罕见），要么是
冗余（常见）。任务是把每个字节归位，然后判定它属于哪一类。

## 环境

```
Python  : 直接调用 conda 环境里的解释器；不要 conda activate（非交互 shell 会失败）
中文输出 : PYTHONIOENCODING=utf-8
jbig2   : pdf_optimize.py 自动从 $JBIG2_BIN / PATH / conda 环境 pdfopt 查找
          安装：conda create -n pdfopt -c conda-forge jbig2enc -y
poppler : <conda-prefix>/Library/bin/  (pdfinfo pdfimages pdffonts pdftoppm)
```

开发机上无 qpdf / ghostscript / ImageMagick，改写一律走 pikepdf。

**云同步目录要当心**：待处理的 PDF 常放在 Dropbox / OneDrive / iCloud 这类目录下，
里面可能是「仅在线」占位符。不要递归列举或做属性扫描，那会触发系统把大量无关文件
从云端拉下来。用 `dir /b <path>` 这类窄命令，只碰任务需要的文件。

## 第 1 步：联网系统性检索（不可省略）

用户明确要求**每个案例都要检索**，不许只凭已有知识作答。至少覆盖：

- 这类文件/这个生产工具的已知膨胀原因（例：`ABBYY FineReader PDF size larger`）
- 相关编码的取舍（例：`JBIG2 vs CCITT G4 vs MRC scanned PDF 2025`）
- 目标操作的具体做法（例：`pikepdf replace image XObject stream`）

把结论写进案例记录并附来源链接。检索也用来**发现自己没想到的冗余类型**。

## 第 2 步：字节归属核算

```bash
pdfinfo file.pdf
python tools/pdf_anatomy2.py file.pdf
```

**核算必须闭合**：各项增量之和 == 文件大小差值。对不上就是还没找全，继续找。

- `pdf_anatomy.py`（v1）**不能给非流对象计价**，字典显示 0 字节。标签树、注释
  压缩在对象流里，必须用 v2。
- 对象数上十万时 pikepdf 逐个解引用极慢（10 万+ 对象要跑十几分钟）。先抽样
  （每 N 个取 1）拿结论，需要精确值再全量跑。

## 第 3 步：逐页编码对比

```bash
python tools/pdf_page_diff.py before.pdf after.pdf
```

**必须递归进 Form XObject。** 很多 OCR 引擎把页面图像包在 Form XObject 里，
不递归会得出「图像消失了」的错误结论。

## 第 4 步：判定新增字节是否携带新信息

**这是全流程的判据，必须做像素分析，不许推测。**

对可疑图像取直方图与形态学特征：

- 8-bit 灰度页里 ~95% 像素是纯黑/纯白、中间灰阶集中在笔画边缘
  → JPEG 振铃伪影，源头是 1-bit，信息增量为零 → **冗余，可去**
- 真彩色照片、插图、有真实灰度层次 → **真信息，不许动**

判断两个位图是否「同一内容」时的可用判据：
- **连通分量数**相同 → 没有字形被增删（但**抓不到符号替换**，替换不改变数量）
- 差异像素是否都落在对方的 1 像素膨胀范围内 → 只是边缘抖动，非内容变化
- 最佳整体位移能否显著降低差异 → 区分「偏移」与「重新二值化」

## 第 5 步：最小改动 + 强制验证

```bash
python tools/pdf_optimize.py in.pdf out.pdf \
    --source original.pdf --jbig2 --strip-tags
python tools/pdf_verify.py in.pdf out.pdf --dpi 300
python tools/pdf_bookmarks.py --from original.pdf --to out.pdf
```

改动越小越好：只替换图像 XObject 的像素载荷，不动几何、不动对象引用，
不可见文字层的对齐关系就天然保持。

**做多个变体做对照**（只重存 / 只修图像 / 修图像+剥标签树），把每项措施的贡献
分离出来——用户需要知道每一步各值多少。

## 第 6 步：写案例记录

```
cases/<短横线-slug>/README.md
```

必须包含：文件大小对照表、**闭合的字节归属核算**、冗余判定的**像素证据**、
修复策略与变体对照表、**验证输出原文**、结论与可迁移经验、检索来源链接。

数据一律贴实测输出，不要复述或概括数字。

# 硬性规则

1. **没有证据不许说「无损」。** 要么给出流的 SHA256 与原始相同，要么给出解码后
   逐像素零差异。渲染比对不算——见规则 3。

2. **验证必须包含渲染像素。** 只查结构会漏掉两类致命错误：
   - CCITT 的 `BlackIs1` 弄反 → 整页反色，而页数/几何/文字层检查**全部通过**
   - 图像错位 → 文字层与图像对不上

3. **在原生分辨率比对。** 300 dpi 位图降到 150 dpi 比较会产生 8–10% 的假差异
   （降采样改变抗锯齿判定），看着像损坏其实没有。

4. **注意参照物是谁。** 拿「清晰的 1-bit 结果」去比「模糊的灰度 JPEG 参照」，
   边缘必然有差异，而且**我们的更忠实**。这种页要改用真正的源文件做逐像素比对。

5. **区分标签树与可搜索文字。** OCR 文字在页面内容流里（不可见渲染模式 `3 Tr`），
   不在 `/StructElem` 里。删标签树不影响搜索/复制/导出，只影响屏幕阅读器和重排。
   **解释清楚让用户自己选**，不要替他决定。

6. **有原始文件就移植原始流**，别重新二值化。移植逐字节无损；重新二值化要过阈值
   判断，必然引入误差。

7. **JBIG2 只用通用模式（`-p`，不加 `-s`）。** 符号模式小 ~30% 但**有损**——它
   聚类替换相似字形，就是施乐扫描仪数字替换事故的成因；对含生僻字的学术文本
   风险不可接受。其无损变体 `-r` 在 jbig2enc 上游已损坏，会直接拒绝执行。

8. **OCR 常常丢书签。** 处理完检查 `get_toc()`，有丢就从原始文件移植。移植时
   **必须重建目的地**：命名目的地（`kind: 4`）跨文档无法解析，`set_toc` 会静默
   退化成 page −1 —— 书签看着在，点了不跳。验证要核对**页码**，不能只数条数。

9. **往云同步目录写成品前先问用户**，那会触发上传。

10. **案例记录不写可识别信息**：不写源文件的书名/标题、文件名里的馆藏号或书号、
    正文摘录、目录与书签的条目文字、本地绝对路径。价值在测量数据和方法，不在
    是哪一本书。文件一律称 `original.pdf` / `ocr.pdf` / `optimized.pdf`，标题类
    内容写成 `<已隐去>`。

# 工具

| 脚本 | 用途 |
|---|---|
| `tools/pdf_anatomy.py` | 快速分类统计（仅流对象） |
| `tools/pdf_anatomy2.py` | 完整字节归属，含对象流内字典计数 |
| `tools/pdf_page_diff.py` | 逐页编码转换对比（递归 Form XObject） |
| `tools/pdf_optimize.py` | 移植原始位图 / 重新二值化 / JBIG2 / 剥标签树 / 重压缩 |
| `tools/pdf_verify.py` | 页数、几何、文字层、渲染像素四重验证 |
| `tools/pdf_bookmarks.py` | 查看 / 跨文件移植书签（重建目的地并校验页码） |

已有案例见 `cases/`，先读一遍最近的那个再动手。
